# 四人共用 main 的轻量协作

目标是几天内做出可演示原型。大家直接在 main 开发即可，不强制分支/PR，不需要每天填正式报告。只保留三件事：**各自 clone、改前同步、小步提交**。

## 协调方式

具体工作和分工由小队讨论确定。一次接口改动让一个人连同前后端一起改完整，比两个人分别猜字段更省事。尽量避免同时大改 App.vue、models.py、types.ts 等公共文件。

四个 Codex 不会自动共享其他会话的上下文。人把本次任务和主要文件告诉各自 Codex；公共接口改变时，把具体字段/例子贴给受影响成员，不能只说“后端改好了”。AGENTS.md 是所有 Codex 的共同起点。

## 每次开工与提交

先确认自己在项目目录、工作区状态与分支；已有修改别直接覆盖。下面适用于已接好远端、团队分支已命名为 main 的情况：

```powershell
git status --short
git branch --show-current
git pull --no-rebase
```

完成一个能解释清楚的小改动、验证后：

```powershell
git diff
git add <这次实际修改的文件>
git diff --cached
git commit -m "补充行程费用展示"
git pull --no-rebase
git push
```

把尖括号替换为实际路径。只有确认工作区全部都是自己这次的改动时，才考虑 `git add .`。不用统一复杂的英文提交格式，中文说明“具体改了什么”即可。

团队统一使用 main；其他人正常 clone 后跟随远端默认分支，不要四人各自初始化同一个项目。Git 状态以实际检查为准。

## 同时改一个文件

改不同区域通常自动合并；改相同区域可能出现文本冲突。先推送的人成功，后推送的人可能被拒绝，需要先拉取合并再推。没有文本冲突也可能有逻辑冲突，例如前端字段名旧、后端字段名新，所以合并后要验证。

冲突时：

1. `git status` 找出冲突文件，读双方改动；不要全选“采用当前/传入”了事。
2. 编辑成正确的最终版本，删除 `<<<<<<<`、`=======`、`>>>>>>>` 标记。
3. 运行受影响的检查，再 `git add <解决的文件>`、`git commit`、`git push`。若又有人抢先推送，再拉取处理。

如果需要退出尚未完成的合并，可以 `git merge --abort`；不确定时先让 Codex 检查状态，不要 reset --hard/clean。**不要 force push main**。冲突处理不是把队友的功能删掉来让编译通过。

## 只需要提前说清的事

- 大改公共文件/接口，简单说：“我接下来改 models.py + types.ts，新增 X，默认值 Y，预计影响 Z”。
- 变更依赖：说明库名与用途，只改必要版本，同步 Python/前端对应锁文件，不为了安装失败清空锁文件。
- 新增需要 Key/数据/模型权重的功能：先写明所需资源、是否可选、缺失时怎么表现，避免队友拉下来无法启动。
- 保存前后端字段、金额单位、坐标系与仓颉协议一致。接口约定见 [API_CONTRACT.md](API_CONTRACT.md)。

## 一个任务何时算做完

用户能走通对应操作；类型/接口对得上；该改动需要的检查实际通过；缺少配置或外部失败有明确表现；新增配置有示例；队友知道改了哪些公共内容。纯文案不必跑一整套测试，普通提交也不必调用收费接口。

交接时发一小段即可：

```text
任务：
改动文件：
接口/配置变化（没有则写无）：
验证命令及实际结果：
交接说明：
提交号（如已提交）：
```

可以贴群里，也可使用 [工作记录模板](TASKS.md)。不要把长聊天记录或密钥提交进来；无需每个微小提交都修改工作记录。

## 数据和源码归属

源码、锁文件、空白配置示例、文档要提交；本地密钥、SDK、依赖、构建产物、数据库不提交。每人历史互相独立。队内共用 API Key 时私下提供，不因仓库是私有就写入 Git；示例和测试使用占位内容。

保留 LICENSE 与来源说明；增加第三方代码、语料或素材时补充来源与使用范围。比赛中的 AI 辅助和团队贡献按实际情况记录，不把参考项目的既有能力算成自己的新增工作。
