## 普通旅行调用链

```text
App.vue（普通旅行）
  → POST /api/plans/generate
  → forecast_trip：每城天气快照 → generate_itinerary：模型与工具
  → Railway.enrich：允许的铁路查询（已订信息随后覆盖）
  → apply_booked_transports → prepare_transfer_anchors → prepare_accommodation
  → Amap.enrich（journey_cities，含出发地，people参与交通推荐）
  → recost_all／normalize_ticket_quantities／绑定费用与攻略
  → 有固定交通时 repair_booking_schedule，否则原排时与用餐修复
  → Validator：共同约束原生校验＋Python专属证据检查
  → Store保存 → 每日地点、跨城卡、真实道路、天气、预算与检查
```

费用使用原项目的 `Decimal`、`cents()` 和权威全员汇总；没有另造一个仅前端计算的预算总数。车票／机票总价留在 `Itinerary.transfers`，车站节点本身不重复收取票款。

## 修改、预订与途中状态

| 模块 | 输入 | 输出与保护 |
|---|---|---|
| `planning_conversation.py`／`planning_conversation_routes.py` | 指令、对话上下文、活动选择、版本指纹 | 意图提案／澄清 → 有界地点核实 → 约束预览；不直接覆盖原计划 |
| `constraint_replan.py`／`constraint_bridge.py` | 单城连续1—3天，每天最多8项，总计24项；预算／时间／交通／锁定／进度 | 真实仓颉2.2有限搜索 → Python独立复核 → 整趟校验、差异、未安排项、未知项 |
| `constraint_storage.py` | 预览编号、父版本／路线／状态修订号 | 原子应用新版本；过期预览409；完成事实单向保护，旧版不能绕开已确认事实 |
| `bookings.py`／`booking_routes.py` | 多段酒店日期／地址、已订交通时刻／站点／全员金额 | 唯一定位、固定接驳、预览再应用；用户声明不冒充订单核验 |
| `transfer_timeline.py` | 查询快照或用户已订交通的实际端点 | 每日出发／到达节点，进出站预留；仅改一天时其他天的已核实节点保持 |
| `local_transport_policy.py` | 真实可用路线、距离、时间、全员费用 | 综合步行负担、费用、通行时间给出推荐原因；查询缺失不等于当地没有该方式 |

`conversation.py` 和原研学问答路由原样保留，规划对话改用 `planning_conversation.py`，避免同名模块误覆盖。

途中变化由用户主动打开并确认当前时间、位置及已完成／漏游内容。系统不从原计划推断“已经完成”，也不自动取消酒店、退票、退款或购买票务。活动取消重算未发生预算；已支付、已承诺和预订费用继续保留。

铁路到达默认不另加统一等待；飞机另留60分钟估算，用户填写的到达额外预留优先。每日站点活动另有可见的5分钟准备节点，市内路耗单算。普通排时整体成功才提交时刻；遇固定点、午夜或最终时间冲突不保存失败方案。前端按后端节点链路显示，不用按时间重排来掩盖错误。首次未订出发段不以模型草稿的下午时刻锁定查询窗口，使用用户可开始时间、当前北京时间和进站预留，并仅从实际查询快照中选择。

仓颉引擎是有限规模搜索和约束工程实现，不宣称原创优化算法，也不承诺任意城市规模下全局最优。代码及依赖许可证继续按原文件保留；SDK运行时通知位于本机编译输出目录，未随本次提交或发布。

## 迁移与验收

新增字段提供默认值，旧普通／研学记录能够读取；天气快照、用户攻略、原文引用及联网参考缓存保留。测试在临时数据库中执行，不向正常使用记录写入合成行程。

本机编译与测试、界面验收、备份位置和外部条件的实际状态见根目录 `MERGE_HANDOFF.md`。历史研学完整效果依赖真实资源包；在线票务、模型、天气、照片与联网搜索效果分别以实际接口响应为准，离线测试不证明这些服务已在线通过。
